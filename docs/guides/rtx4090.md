# One RTX 4090 workstation

## Install the complete stack with one command

On a dedicated Ubuntu 22.04/24.04 amd64 GPU host:

```sh
sudo bash scripts/onprem/install-rtx4090.sh
```

The [native installer guide](../../scripts/onprem/RTX4090.md) includes the
fresh-host bootstrap command, CPU/RAM/disk requirements, driver reboot/resume,
interactive administrator setup and SSH-only browser access. It installs native
K3s rather than nesting another cluster inside Docker.

The installed profile uses **GPT-OSS 20B (MXFP4/BF16), EmbeddingGemma 2 (text-only,
768 dimensions, BF16), and Whisper large-v3-turbo (FP16)**. All three models run
on the same GPU, with fractions 0.66/0.07/0.12, no CPU weight offload, and one
chat sequence with a 16384-token context. Startup order is speech → chat → embeddings.

On Ubuntu 22.04.5 and a 24GB RTX 4090, all three Pods were Ready simultaneously;
CUDA operations used the same GPU UUID; Japanese query/document embeddings,
Japanese chat, function calls and timestamped speech transcription passed.
Measured usage after real requests was **20,561 / 24,564 MiB**. See the
[recorded installation and inference evidence](../verification/native-rtx4090-install-2026-11-11.json).
This does not establish sustained-load or complete VideoQ learning-journey acceptance.
The application/runtime release is verified; the source-built CUDA embedding
image and source inference chart are separate, digest-pinned local deployment inputs.

## Alternative Qwen sharing candidate

This candidate profile targets **one physical RTX 4090 (24 GB), native Ubuntu
22.04/24.04 LTS amd64 and single-node K3s**. Chat, embeddings and transcription remain
separate inference containers in three Deployments. All three models execute on
CUDA. The API, web, database, storage, queue, processing orchestration and speech
input normalization use the CPU. DGX Spark and AMD/ROCm are outside this profile.

**Hardware acceptance for this Qwen variant is pending.** The measured GPT-OSS
profile above does not prove the different Qwen models fit or meet quality and
latency requirements. Do not treat the candidate as a supported production
recipe until the acceptance checklist below passes on the actual workstation.

## How one GPU serves three Pods

NVIDIA Device Plugin **time-slicing** advertises three
`nvidia.com/gpu.shared` slots from the one GPU. Each inference container reserves
one shared slot; it never reserves an exclusive `nvidia.com/gpu`. The speech
normalization sidecar reserves no GPU. The existing three private service URLs,
model caches, per-service restarts and application settings remain separate.

This is sharing, not three physical GPUs or isolated VRAM partitions. CUDA
processes compete for the same compute, memory and failure domain. The configured
vLLM fractions are per-process planning budgets, **not enforced GPU memory
isolation**. A process crash/OOM can affect peers. Use one physical GPU and do not
run desktop GPU workloads, other models or additional inference replicas alongside
this profile. Do not enable a second GPU device plugin or install these settings
into a workstation managed by GPU Operator without reconciling its configuration.

| Role | Immutable model | VRAM fraction | Concurrent sequences |
| --- | --- | ---: | ---: |
| Chat | Qwen3-1.7B, revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e` | 0.25 | 1 |
| Embeddings | Qwen3-Embedding-4B, revision `5cf2132abc99cad020ac570b19d031efec650f2b` | 0.43 | 1 |
| Speech | Whisper large-v3-turbo, revision `41f01f3fe87f28c78e2fbf8b568835947dd65ed9` | 0.14 | 1 |

The 0.82 total leaves headroom for the driver/runtime. Chat/embedding contexts
are bounded to 16384 tokens, CUDA graph capture is disabled, and CPU model offload
is disabled. Speech upload and upstream concurrency are one. Embeddings retain
VideoQ's 1536-dimensional contract and model identity; existing CPU embeddings are
not silently relabeled. Follow the normal reindex procedure when changing the
embedding model. Chat uses the smaller 1.7B model to reserve room for GPU
embeddings and speech; its answer/tool-call quality requires actual evaluation.

Models start in order: embeddings, speech, chat. Readiness init containers wait
for each predecessor's real health endpoint before the next vLLM process starts,
reducing overlapping startup memory profiling. This does not promise steady-state
memory isolation. The application should be started only after all three services
are Ready. After an OOM, stop all three inference Deployments and investigate;
do not keep restarting busy models with larger memory fractions.

The three GPU containers reuse the same patched, audio-capable, signed
`videoq-vllm` release image. No unmodified upstream/nightly image or new blanket
security exception is introduced. The existing image vulnerability and signature
gates remain required. The upstream-engine adoption in PR #1179 is a separate
migration from the single-GPU scheduling configuration described here.

## Prepare the workstation

1. Check out the reviewed source containing this profile. Use the existing
   [K3s host/dependency guide](on-premises-k3s.md) for the application, PostgreSQL,
   private storage, queue and secrets. A Git clone alone does not install these
   dependencies or model weights. The GPU is not a replacement for host RAM/CPU.
2. Install NVIDIA's Ubuntu driver and Container Toolkit using the official
   [toolkit instructions](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).
   Follow [K3s NVIDIA runtime setup](https://docs.k3s.io/advanced#nvidia-container-runtime-support).
   K3s must detect `nvidia-container-runtime`; restart K3s after installing it and
   verify `kubectl get runtimeclass nvidia`. Choose the driver supported by the
   CUDA version in the exact verified release image, rather than copying a driver
   minimum from another machine.
3. On the workstation, run the read-only host check:

   ```sh
   python3 scripts/gpu/rtx4090-preflight.py
   ```

   It refuses other OS/architectures, another GPU model or multiple physical
   GPUs. It reports identity only; it does not run any models. The profile's
   inference requests total 3.25 CPU cores and 14.5 GiB RAM before model download
   init containers, K3s, the OS and all VideoQ dependencies. Container memory
   limits total 28 GiB for inference alone. These are configuration values, not
   a measured whole-machine minimum; size the complete stack before purchase or
   installation. Persistent model claims request 40 GiB, with additional space
   needed for container layers and application/database/media storage.
4. Select the single local node and explicitly label it:

   ```sh
   NODE=REPLACE_WITH_LOCAL_NODE_NAME
   kubectl label node "$NODE" videoq.io/inference-target=rtx4090
   ```

5. Install NVIDIA Device Plugin v0.20.1 with the reviewed time-slicing values:

   ```sh
   helm upgrade --install nvdp nvidia-device-plugin \
     --repo https://nvidia.github.io/k8s-device-plugin \
     --version 0.20.1 --namespace nvidia-device-plugin --create-namespace \
     -f charts/videoq-inference/examples/rtx4090-device-plugin.yaml
   kubectl get node "$NODE" -o jsonpath='{.status.allocatable}'
   ```

   Expect `nvidia.com/gpu.shared: 3` and no exclusive `nvidia.com/gpu` capacity.
   `renameByDefault: true` makes accidental use of the three-whole-GPU profile
   fail to schedule. `failRequestsGreaterThanOne: true` rejects a request for two
   shared slots; that would not reserve a larger compute or memory share anyway.
   The plugin is limited to nodes carrying the explicit RTX 4090 label.

## Install the candidate inference profile

For **private pre-merge hardware acceptance**, use the reviewed source chart and
source-built/scanned images pinned to immutable registry digests. Record the
source SHA, build/scan evidence and all image/model identities. The preflight
script verifies image digest syntax and hardware allocation; it does **not**
verify attestations. This source-build test is not a signed release or production
promotion. The normal signed release workflow is main-only, so signed distribution
verification follows merge and is required before production rollout.

The following commands describe the **signed-release installation path**, once
the reviewed change has been merged and released:

Download and verify the [signed release and both charts](on-premises-releases.md).
The release must contain these chart changes. Use the **verified chart archive**,
not an older chart that cannot understand GPU sharing. The verified source and
chart must match this checkout; do not pair a candidate source chart with an old
release and call that signed candidate acceptance.

```sh
# Substitute the actual verified archive paths from your reviewed release.
INFERENCE_CHART=/secure/videoq-release/videoq-inference-REVIEWED_VERSION.tgz
APPLICATION_CHART=/secure/videoq-release/videoq-REVIEWED_VERSION.tgz
helm upgrade --install inference "$INFERENCE_CHART" \
  --namespace videoq --create-namespace \
  -f charts/videoq-inference/examples/rtx4090.yaml \
  -f /secure/videoq-release/verified-inference.json
kubectl -n videoq rollout status deployment/videoq-inference-embedding --timeout=30m
kubectl -n videoq rollout status deployment/videoq-inference-whisper --timeout=30m
kubectl -n videoq rollout status deployment/videoq-inference-chat --timeout=30m
python3 scripts/gpu/rtx4090-preflight.py --node "$NODE" --namespace videoq
```

The last check requires three Ready Pods on that node, immutable image digests,
three shared GPU allocations and a real CUDA FP16 operation in each allocated
container. All three must report the host's one physical GPU UUID. This is a
hardware/allocation check, not proof of model quality or the complete learning
journey. Keep its JSON evidence private with the site's acceptance records.

Install VideoQ with your existing site configuration, the normal
`charts/videoq/examples/local-ai-vllm.yaml` application overlay and the verified
image lock **last**. Retain the site's secrets, storage and private service URLs.
Use that overlay for all three endpoints; do not retain hosted AI defaults.

```sh
helm upgrade --install videoq "$APPLICATION_CHART" --namespace videoq \
  -f /secure/videoq-site.yaml \
  -f charts/videoq/examples/local-ai-vllm.yaml \
  -f /secure/videoq-release/verified-images.json
```

For an intentional network-isolated run, pre-provision model caches, apply
`downloadModels=false,networkPolicy.denyEgress=true` and use K3s network-policy
enforcement. The inference policy permits only same-release peer readiness and
CoreDNS DNS egress; it does not grant public model downloads. Other application
network policies and host-level egress controls remain necessary to prove offline
operation.

## Runpod preliminary model/VRAM probe

Runpod offers RTX 4090 Pods, but its ordinary GPU Pod is itself a container and
has restrictions on nested Docker/Compose. Use this only to measure three real
vLLM model processes sharing one allocated 4090. The production configuration
remains three independent Kubernetes inference containers; K3s scheduling,
Device Plugin sharing, NetworkPolicy and the full application journey still need
a GPU VM or the actual workstation. A passing Runpod probe is never K3s acceptance.

The helper exports model commands from the real Helm profile, rather than keeping
a second set of model revisions, aliases or VRAM fractions. It rebinds listeners
to loopback, changes the embedding port to 8001 (the two production Pods each have
port 8000 in separate network namespaces), and relocates the model root. All model
arguments and CUDA inference roles otherwise remain unchanged.

1. Verify a reviewed runtime release with `onprem-release.py` as described above.
   For a private candidate test using an existing signed runtime, independently
   confirm `apps/inference/whisper` is byte-identical between that runtime's source
   and the candidate. This proves source equivalence only; it does not sign the
   candidate chart. Record both source identities and the runtime image digest.
2. From a clean committed checkout, export a new plan locally:

   ```sh
   HELM_BIN=helm node scripts/gpu/export-rtx4090-probe.mjs \
     /secure/videoq-release/verified-inference.json /secure/rtx4090-probe-plan.json
   ```

   This only writes a private JSON file. It does not create an instance, transmit
   credentials or start billing. Dirty-source plans are refused by the GPU runner.
3. Before renting, confirm the current quote and total spending/time limit. Use
   **one** RTX 4090, a host driver compatible with the exact image's CUDA runtime,
   enough host RAM and container disk for the image, approximately 13 GB of model
   weights and runtime caches. The current reviewed CUDA 13.0.2 image requires a
   suitable CUDA 13 host; do not substitute a different GPU/image to get capacity.
   Configure provider-side automatic termination independently of the test script.
   Do not attach an existing site volume or load production/user credentials.
4. In that exact digest-pinned runtime image, put the reviewed source and plan in
   private writable locations. The image's normal `vllm serve` entrypoint must be
   overridden for the probe; Runpod's REST API exposes `dockerEntrypoint` and
   `dockerStartCmd` for this. No inference port needs public exposure.

   ```sh
   python3 scripts/gpu/runpod-rtx4090-probe.py provision /secure/rtx4090-probe-plan.json \
     --model-root /tmp/videoq-probe-models --output /tmp/videoq-provision-result \
     --max-seconds 1800
   python3 scripts/gpu/runpod-rtx4090-probe.py probe /secure/rtx4090-probe-plan.json \
     --model-root /tmp/videoq-probe-models --output /tmp/videoq-probe-result \
     --max-seconds 1800
   ```

   Provisioning finishes before model serving begins. The probe then loads all
   three models offline, runs three rounds of concurrent Japanese chat, a real
   finite 1536-dimensional embedding and the checksum-pinned public FLEURS Japanese
   audio through Whisper. Timestamp/CER checks use the existing threshold below
   0.25. GPU memory/utilization are sampled every 0.5 seconds; the reported sampled
   peak is not an exact allocator high-water mark or a VRAM guarantee.
5. Retrieve `result.json` and private per-role logs before terminating the owned
   disposable Pod/disks. The runner stops only process groups it created, on both
   success and failure. Its invocation deadline/cleanup is not a cloud billing
   control: the operator/provider must ensure termination. The declared image in
   its report must be checked against Runpod's actual Pod configuration externally.

The runner has no CPU/GPU-substitution mode and never declares full application,
K3s or production acceptance. Local HTTP/process fixtures exercise its failure and
cleanup contracts only; they do not execute or validate GPU models.

References: [Runpod GPU types](https://docs.runpod.io/references/gpu-types),
[Runpod container restrictions](https://docs.runpod.io/tutorials/pods/build-docker-images),
[current pricing](https://www.runpod.io/pricing).

## Updates, recovery and remaining acceptance

Before changing model revisions or memory fractions, stop processing intake and
scale **all three** inference Deployments to zero, wait for their Pods to disappear,
then perform the Helm upgrade. A mixed old/new memory budget can exceed VRAM even
when each individual profile passes validation. Model claims are retained. Restore
the matching profile and image lock together when rolling back; test against a
backup/restored copy of persistent application data before production promotion.

On an actual RTX 4090, retain evidence for all of the following:

- Exactly one 4090 and three shared allocations; actual CUDA checks in each Pod.
- Cold provisioning, ordered startup, cached restart and individual service restart
  without Pending GPU requests or OOMs. Measure host RAM, VRAM peak and latency.
- Real video upload, GPU transcription, GPU embedding/index creation and cited,
  streamed GPU chat. Verify vectors have 1536 dimensions and the correct identity.
- A real upload/indexing job while a learner chats; bounded admission/concurrency,
  no CPU or cloud fallback, and acceptable measured peak VRAM and latency.
- Japanese transcription and answer/tool-call quality on the site's content;
  protected video citation seeking, backup/restore and update/rollback.
- The normal required CI and NVIDIA image security scan for the exact candidate
  source. After review/merge, verify signed publication and anonymous image pulls
  for the corresponding main release before production promotion.

Until the source/hardware checks pass, leave the integration PR in Draft. Signed
release verification is a separate post-merge promotion gate. CPU-hosted tests and
synthetic scheduling fixtures are useful regression evidence but do not satisfy
this hardware gate. If the memory budget fails in practice, tune models or add
explicit job/model scheduling while retaining GPU execution for all three roles;
never silently replace embedding or transcription with CPU inference.
