# 大きな講座の知識読込を一括化する

講座51の全905チャンクを使う処理を点検したところ、候補生成の各回で知識を1件ずつ読んでから分類の保存ステップを再生していた。D1は有料プランでもWorker 1回あたりの問い合わせ上限が1,000回で、1クエリのバインド上限は100個である。[Cloudflare公式仕様](https://developers.cloudflare.com/d1/platform/limits/)で確認した。

元の検証DBを複製し、実際のランタイム工場に同じ1,000回の上限を適用すると、1,001回目の問い合わせで上限エラーを再現した。エラー処理を含めた計数は1,003回となり、モデル要求前に止まった。これは文書化された制約を模したローカル試験であり、本番Workerで障害を発生させた試験ではない。

知識を80キーずつ取得する `cachedMany` をSQLリポジトリへ追加した。所有者・現行入力スナップショット・リース・講座への登録を従来と同じSQL条件で検査する。入力キーを重複排除し、SQLの返却順に依存せず、チェックポイント順に戻してから分類へ渡す。保存済み分類の入力とキャッシュキーを変えないための順序維持である。単件読込のみを実装したアダプタのフォールバックは逐次のまま残す。DBスキーマや課金・失敗回数・モデルの指示は変更しない。

修正後の同じ複製試験は110問い合わせで、最初の `skill_draft` 要求の境界まで進んだ。その要求はローカルで遮断し、外部モデルへの転送は0回だった。元のDBファイルは試験前後で同一であり、失敗ジョブや実利用回数には変更がない。これは問い合わせ数と保存済み分類の再利用を確かめる試験であり、本文生成が成功したという主張ではない。

合成905チャンクを使う回帰テストでは、知識の読込が12クエリ、候補組立全体が13クエリであること、順序・重複排除・バインド数100個以下を確認した。変更前の契約テストは1件失敗・19件成功、変更後はD1の関連25テストと、隔離したPostgreSQL17の20契約テストが成功した。検証用コンテナは停止済みである。APIの型検査3構成と変更ファイルのlintも成功した。[証拠記録](evidence/course-skills-knowledge-read-batching-2026-11-28.json)に計測とソースのハッシュを保存した。

この修正についてのリモートCIと、実モデルでの講座再構築は未完了である。追加利用枠と新しい再構築は引き続き承認待ちで、今回の試験による外部推論・本番変更・公開・デプロイ・マージは行っていない。
