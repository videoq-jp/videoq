# 草案の回数制限付き修正

対象: #1744。既存の意味監査で問題が見つかった生成草案を、出典を固定したまま最大2回修正・再監査する。所有者の編集内容は自動で書き換えず、所有者の編集APIは従来どおり検査結果を返す。

## 動作

1. タスクと知識を固定して草案を生成し、形式・出典参照・意味監査を行う。
2. 意味監査が不支持、または指摘を残した場合に限り、指摘と固定した根拠を使って修正する。
3. 修正後も同じタスクslugと出典参照を検査し、意味監査を再実行する。
4. 指摘がなくなれば所有者レビュー待ちにする。直らなければ最大2回で打ち切り、公開不可の候補として保留する。
5. 修正案の参照・構成が不正な場合は直前の検査済み草案を保持する。モデル生成失敗も修正試行として記録する。

修正の生成失敗を段階キャッシュに保存し、チェックポイントから再開しても同じ失敗を再課金で呼び出さない。途中再開では成功済みの生成・監査も再利用する。各maintenance tickのモデル呼び出し最大1回と、既存の累積予算・リース・入力スナップショットの検査を維持する。自動でジョブを作り直したり予算をリセットしたりしない。

初回監査の支持・指摘件数、各修正の試行番号と結果・指摘件数を候補の`generationRepair`へ保存する。履歴に長い指摘本文を重複保存して候補サイズの上限を圧迫せず、最後の指摘を`issues`へ残す。新規生成の版は`course-draft-v4-bounded-repair`。無関係な動画追加で既存のレビュー作業を再び結び付ける場合は、既存の本文・修正履歴・生成版を保持する。

## 検査

- 単体試験: 1回での修正成功、2回での打ち切り、不正な出典参照を含む修正案の拒否、予期しない内部例外の伝播。追加4件は修正前の実装では失敗した。
- D1実DB: 修正後の合格、2回とも不支持、修正生成の失敗をそれぞれ複数tick・リースで実行。呼び出し数は各tick最大1回、修正最大2回、総呼び出し数は6・8・6回。知識キャッシュは不変、公開レコードは0件だった。
- 既存D1実行経路: 無関係な動画追加で所有者の修正済み本文と既存の生成版を保持し、公開・MCP取得・出典除去による失効まで確認。
- 関連API 6ファイル37テスト、翻訳キー10テスト、APIの全型検査と変更箇所lintは成功。API全体も同時実行数2で397ファイル3,937テストが成功し、条件付き129ファイル1,605テストはスキップだった。Workers実行環境の16ファイル118テストも成功した。

これらは固定応答モデルによる制御・保存・再開の試験である。実データで生成品質が改善したという証拠にはしない。監査が誤って支持と判定した例はこの修正分岐に入らないため、動画120で確認した意味的な品質問題は未完了のままである。修正が合格しても公開操作と内容ハッシュに結び付く所有者レビューが必要になる。
