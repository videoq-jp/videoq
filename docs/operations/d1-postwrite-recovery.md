# D1書き込み後のPostgreSQL復旧演習

2026-11-15実施。**合成データによる隔離演習は成功。本番切り戻しの受け入れ基準はまだ未達。**

後続の[版付き画像・全量バックアップ検証](d1-visual-full-backup-recovery.md)で、以下の未対応項目1・2を追加検証した。この文書の実測値は先行する合成データ演習の記録である。

D1に書き込んだ後のNeonへの接続先変更だけでは、作成・更新・削除を失う。本演習は停止したD1の最終状態を、事前に基準データを入れたローカルPostgreSQLへ反映し、削除も含めた照合を行う。差分CDCや双方向同期は導入しない。

## 実測した範囲

実際のCloudflare D1（独立した20件のマイグレーション）と768／1536次元の実Vectorize、専用Docker PostgreSQL/pgvectorを使用した。API・Lambda・LLMは起動せず、合成データの唯一の書き込み元は演習スクリプトとした。本番DB・バックアップは変更していない。

- 共通56テーブルを照合。実データを入れたのは10テーブルで、残り46テーブルは空の一致を検証した。全テーブルの全業務機能を検証したという意味ではない。
- 基準コピー作成後、D1でユーザーと動画を削除、動画を追加・更新、利用量を更新。完了済みジョブとOutbox、LMS設定、パスワードとセッション、コース所属関係を復旧した。
- 削除ユーザーのセッションも復旧先に残らないことを確認。パスワードはBetter Authの実ハッシュ検証で照合した。外部OAuthやHTTP Cookieの互換性を証明するものではない。
- JSONの `9007199254740993` を丸めず保持。日時・Boolean・NULL・JSON・配列等は既存の順方向マッピングと逆変換し、再度順方向へ正規化して全共通テーブルを比較した。JSONの数値字句を保持した比較により、キー順・空白・小数表記の違いと値の違いを区別する。
- D1の所有権・公開リビジョンと実Vectorizeから取得したベクトルを検証し、シーン2件をpgvectorへ再構成。両次元で所有権とcosine類似検索を確認した。Embedding再生成はしていない。
- 会話チェックポイント1件と保留書き込み1件をPostgreSQL saver形式へ再構成。実`PostgresSaver.getTuple()`で本文・バイナリ・メタデータ・保留書き込みを読み出した。バイナリはBuffer/Uint8Arrayのクラス同一性ではなくバイト列を比較する。指数表記の数値チャンネルバージョンも検証した。
- 復旧を再実行し同じ指紋になること、復旧後の動画ID採番が最大IDを超えることを確認した。
- 制約違反を意図的に発生させ、DELETE後の途中失敗でも基準コピーの行データが戻ることを確認した。処理中ジョブ、不完全な表一覧、欠損・別所有者のベクトル、未対応の画像参照は拒否した。
- 旧テーブル27件を模した独立した番兵テーブルの不変性を確認した。これは**実際の旧Django/OAuth 27テーブルや本番バックアップを再検証したものではない**。

最終演習は16項目成功、単体テスト20件成功。型チェックと対象ファイルのlintも実施。根拠は [実行結果](evidence/d1-postwrite-recovery-2026-11-15.json) に記録する。

初期試行の失敗も保持した。最初は合成ユーザーの必須列不足で停止、次に同一バイト列をBuffer/Uint8Arrayの厳密クラス一致で比較して停止した。フィクスチャと比較を修正後に再実行し、最終版が成功した。最初から無修正で成功したという記録ではない。

## 実装と実行条件

`scripts/d1-postwrite-rehearsal.ts` は合成データ限定の演習コマンドで、`scripts/migrations/d1/postwrite-recovery.ts` が逆変換と復旧を行う。**本番用のインポートCLIではない**。以下の防御を持つ。

- PostgreSQLはループバック接続のみ。合成演習の復旧先は毎回新規のランダムな `recovery_<32桁hex>` スキーマと、その会話用スキーマに限定する。
- D1は新規の空DBで、名前が `videoq-recovery-<日付>-v<番号>-db` に一致し、表一覧がマイグレーション契約と一致することを要求する。
- 処理中ジョブ・会話リース・未完了Outbox・索引同期などを拒否する。**これだけで外部ライターを停止できるわけではない**。本演習はWorker/キュー等を接続しない新規DBを使い、唯一の書き込み元を停止したうえで最終状態を2回比較する。
- 各表1000行、D1スナップショット16MiBまでの予算とする。後続の全量隔離演習には明示的な上限拡張を設けるが、本番用CLIではない。
- 復旧先の共通テーブルをロックし、依存順で削除・挿入する。`CASCADE`で未知の参照を削除せず、未知の外部キー制約があれば失敗させる。
- 採番は `setval` でなく、同一トランザクション内の `ALTER SEQUENCE ... RESTART` を使う。[PostgreSQL公式仕様](https://www.postgresql.org/docs/17/sql-altersequence.html)に従う。
- 本文・トークン・ハッシュ済みパスワード・ベクトルは結果ファイルに出力せず、件数と指紋のみを出力する。合成設定・作業ファイルは所有者専用のディレクトリとファイルに保存する。

再実行時は、専用D1、専用Vectorize2件、専用のローカルPostgreSQLを新しく用意し、D1マイグレーションを適用する。D1やVectorizeを本番Workerへバインドしない。Node.js 24以降と、このリポジトリで固定した依存を使用する。D1の管理APIは[公式のバッチ形式](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/)を使用する。

所有者専用の設定ファイル（0600）には `accountId`, `databaseId`, `name`, `token`, `postgresUrl`, `expiresAt` を指定する。`name` はDB名の `-db` を除く共通接頭辞。`expiresAt` は2時間以内のISO日時とする。実際の認証値はチャットや引数へ貼り付けない。

```sh
cd apps/api
npx --no-install tsx scripts/d1-postwrite-rehearsal.ts \
  --config /private/operator/recovery-config.json \
  --output /private/operator/recovery-result.json
```

実行結果にかかわらず、管理者は専用リソースを削除し、不在を確認する。スクリプトのfinallyはPGの専用スキーマを削除するが、CloudflareストアとDockerコンテナの撤去は別の工程である。今回の実行ではD1・Vectorize2件・コンテナと匿名ボリュームの削除および一時コピーした操作資格情報の削除を確認した。既存の移行検証DB2件は維持した。

## 本番切り戻し前に残る条件

1. **版付き画像オブジェクトの復旧**。D1の `object_version`／`publication_version` を現在のPostgreSQLスキーマでは保持できない。先行版は空でない場合に処理を拒否した。後続版はスナップショットに結び付いた画像復旧証明を要求する。画像マニフェスト・フレーム等の保存先を含む互換変換／コピーと整合性照合が必要で、DB列の黙った破棄は認めない。
2. 本番全量バックアップの復元コピーを使い、旧27テーブルの実データ・制約も含めて保持を再確認する。今回の復旧先DDLは現行Drizzleスキーマから生成し、履歴全体を復元したものではない。
3. 全量スナップショットの一貫性と外部ライターのフェンス、容量制限、RTO/RPO、キューとストレージの再開、Stripe等の外部副作用を含む運用手順を確立する。
4. 実際の外部認証・Cookie・ジョブの再開・画像を含むAPI/E2Eを復旧先で確認する。今回のチェックポイントはsaver読み出しまでで、エージェント実行の再開までは検証していない。

この演習だけでD1書き込み後の本番Neon切り戻しを安全と判定しない。既存の本番切り替え停止条件を解除しない。
