# 版付き画像と全量バックアップ復元コピーの復旧検証

2026-11-15実施。D1側の変更をローカルPostgreSQLへ戻す隔離検証が成功した。本番切り替え、PRのマージ、本番データへの書き込みは行っていない。

## 検証範囲

検証済みの完全バックアップを専用PostgreSQL/pgvectorコンテナへ復元し、91テーブルの件数と制約を確認した。そのDBの独立したクローンを復旧先にした。現行アプリのエクスポートは62テーブル・9,854行で、共通56テーブルのほか、シーン・チェックポイント・画像状態を含む。旧Django／OAuthの実27テーブルはD1に移さず、復旧先に保持した。

実際のD1マイグレーションを適用したローカルworkerdへ現行データを投入し、通常の索引同期処理を通した。全量検証のベクトルプロバイダーは決定的なメモリ内シミュレーターである。実Cloudflare D1・実Vectorize両次元の合成データ演習は[先行検証](d1-postwrite-recovery.md)で別途実施しており、今回の全量検証がリモートVectorizeの負荷や検索品質を保証するものではない。

隔離D1に動画・ユーザーを追加し、既存動画を更新・削除して利用量も変更した。最終状態を取得し、共通56テーブルを依存順に置き換えた。逆変換後に全値を再正規化して照合した。削除動画の25シーンも除去され、復旧したシーンは2,165件、チェックポイントは643件、保留書き込みは981件だった。全643チェックポイントを実`PostgresSaver.getTuple()`で読み出した。エージェント実行の再開はこの検証に含まない。

実27テーブルは構造・行データの指紋が保存方針ファイルと一致し、全制約が検証済みであることを復旧後にも確認した。認証情報、行データ、本文、ベクトル、接続資格情報を公開証跡には含めない。

## 画像の互換復旧

`recoverVisualArtifacts` はD1の版付きチャンクを、PostgreSQL版の読取処理が扱える独立した保存先へコピーする。元オブジェクトを変更せず、所有関係、チャンク範囲、JPEG境界、サンプル、マニフェストと版の一致を検証する。全参照を確認した後にルートマニフェストを最後に公開する。別内容の既存保存先は拒否し、同一バイト列なら再試行できる。オブジェクトの検証結果は同じスナップショットに結び付いたプロセス内証明としてDB復旧処理へ渡す。証明なしの版情報破棄は引き続き拒否する。

元データの画像処理5件はいずれもerror状態だった。読み取り専用の本番R2バインディングから実チャンクを取得し、ローカルR2へコピーした。これに隔離環境でready状態の合成画像処理1件を追加した。本番R2へのPUT・削除は行っていない。復旧先ではPostgreSQLの実Evidence Repositoryで所有者にだけ動画を返すことを確認し、その結果を使って実`readVisualManifest`／`readFocusFrames`から元JPEGと同一の画像を取得した。

別途、合成JPEGをブラウザーで表示し、64×64ピクセルとして読み込まれたことと青い画像の実表示を確認した。これは画像読取経路の検証であり、VideoQ全画面のOAuth付きE2Eを実施したという意味ではない。本番画像をブラウザーに表示していない。

## IDとトランザクション

本番バックアップの一部のID列は`GENERATED ALWAYS`だったため、元IDの挿入には`OVERRIDING SYSTEM VALUE`を使用する。現行DDLだけを生成する合成試験では見つからなかった差異である。

既存13系列のうち6系列は、採番位置が現存行の最大IDより進んでいた。復旧後に削除済みIDを再利用しないよう、D1の`sqlite_sequence`、復旧前PostgreSQLの発行済み位置、復旧行の最大IDの最大値を超える位置へ、トランザクション内で`ALTER SEQUENCE ... RESTART`する。D1採番情報が欠けた場合は失敗させる。

全量検証の再生時は、検証済みアーカイブの採番床と、実施した管理下の書き込みから最終D1採番を導出した。生きたD1から採番情報を再取得した証跡ではない。この限界を補うため、追加の自動統合テストでは実ローカルD1の`sqlite_sequence`を読み、挿入後に削除した500・9000、PostgreSQL側の先行位置、再実行、失敗時のロールバックを確認する。実運用では停止済みD1から採番情報も同じ整合したスナップショットとして取得する必要がある。

## 実装の安全境界と再検証

通常の復旧先はループバック上のランダムな専用スキーマに限る。完全バックアップをそのまま復元する場合に限り、`recovery_<32桁hex>`という専用DB名を明示し、`current_database()`との一致を確認したうえで`public`／`chat_memory`を使う。本番DB名やリモート接続は許可しない。既定予算は1表1,000行・16MiB、明示的な隔離検証の上限は1表10,000行・512MiBである。本番用の復旧CLIではない。

追加テストは`apps/api`で実行する。

```sh
npx --no-install vitest run test/persistence/d1-postwrite-recovery.test.ts test/persistence/d1-visual-recovery.test.ts
# ローカル専用のPostgreSQL/pgvector接続を環境変数に設定して実行
npx --no-install vitest run test/persistence/d1-recovery-identity.integration.test.ts
```

統合テストは`PERSISTENCE_TEST_DATABASE_URL`を使い、ランダムな専用スキーマを作成・撤去する。CIの既存PostgreSQLサービスで実行できる。全量の私有入力と検証ログは所有者だけが読める場所へ保管し、公開するのは[集計証跡](evidence/d1-visual-full-backup-recovery-2026-11-15.json)のみとする。

## 検証中に見つかった問題と残る条件

初回の全量チェックポイント読取は一括取得によりworkerdがメモリ不足となり、16行単位の取得とBLOBのhex表現へ変更した。ローカルランタイムの対応日を超えたcompatibility dateも修正した。実データから公開run IDとsource revisionの違いを確認し、検索世代の照合を修正した。PGへの初回反映はID列の制約で失敗してロールバックし、原因を修正して成功した。検証用ストレージの永続化オプションが新Miniflareで無効だったため、読取専用ソースから再構築し、対応する`resourcePersistencePath`で再試行した。これらを最初から成功した検証として扱わない。

残る本番受け入れ条件は、外部ライターの停止と整合した全量取得、実OAuth・Cookie、キュー／外部副作用を含む再開、RTO/RPO、性能・検索品質・費用の最終評価である。本結果だけで本番切り替えの停止条件は解除しない。
