# RTX 4090を1枚搭載した筐体で動かす

対象は **RTX 4090 1枚（24GB）、Ubuntu 24.04 LTSのamd64、単一ノードのK3s** です。
チャット・検索用の埋め込み生成・文字起こしは、独立した3つの推論コンテナでCUDAを使います。
API・Web・DB・ストレージ・キュー・処理の制御・音声入力の正規化はCPUで動きます。
DGX SparkやAMD/ROCmは今回の対象に含めません。

**実機検証は未完です。** この設定の作成時点ではRTX 4090の実機がなく、モデルの同時常駐、
VRAMピーク、速度、日本語の品質は確認できていません。設定の検査やCPU上のCIの成功を、
4090での稼働保証として扱わないでください。導入前に末尾の受入項目を実機で検証します。

## 3つのPodでGPUを共有する仕組み

NVIDIA Device Pluginのtime-slicingで、物理GPU 1枚から
`nvidia.com/gpu.shared` を3枠公開します。各推論コンテナは共有枠を1つ要求します。
音声の正規化を行うsidecarはGPUを要求しません。既存の3つの非公開Service、
モデル用の永続ボリューム、個別の再起動は維持します。

共有枠は物理GPUやVRAMの分割ではありません。計算・VRAM・障害の影響範囲は共通です。
vLLMのメモリ使用率は各プロセスの予算であり、強制的なメモリ隔離ではありません。
ほかのGPU処理や推論レプリカを同じGPUで動かさず、OOM時は3つの推論Podを停止して調査します。
GPU Operatorや既存のDevice Pluginがある環境に、別のDevice Pluginを重ねて導入しないでください。

| 用途 | モデル | VRAM予算 | 同時シーケンス数 |
| --- | --- | ---: | ---: |
| チャット | Qwen3-1.7B | 0.25 | 1 |
| 埋め込み | Qwen3-Embedding-4B | 0.43 | 1 |
| 文字起こし | Whisper large-v3-turbo | 0.14 | 1 |

モデルはそれぞれ不変のリビジョンで固定します。合計0.82とし、ドライバー等の余裕を残します。
チャットと埋め込みのコンテキストは4096トークン、CUDA graphは無効、CPUへのモデルオフロードも
無効にします。文字起こしの同時アップロード・上流並列数は1です。
埋め込みは既存の1536次元を維持します。既存CPU埋め込みを別モデルの出力として扱うことはせず、
モデルを変更する際は通常の再インデックスを行います。
チャットに小さい1.7Bモデルを選んだのは、残る2つもGPUで実行するためです。回答とツール呼び出しの品質検証は必要です。

起動は埋め込み→文字起こし→チャットの順です。前のモデルのhealthが成功してから次を起動し、
初期化時のメモリ計測が重なるのを抑えます。アプリは3つの推論ServiceがReadyになってから起動します。
3モデルはダイジェスト固定した同じ上流 vLLM を使います。音声依存4パッケージはハッシュ固定し、別ボリュームから読み取り専用で読み込みます。推論エンジンの再ビルド・再配布は行いません。上流イメージ・音声依存の検査と、署名付き Chart の検証を必須にしています。

## ホストと共有GPU枠の準備

1. この設定を含むレビュー済みソースをcheckoutします。
   [K3sの導入手順](on-premises-k3s.md)でアプリ、PostgreSQL、ストレージ、キュー、秘密情報を準備します。
   cloneだけではこれらやモデルは導入されません。
2. NVIDIAの[Container Toolkit手順](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)と
   [K3sのNVIDIA runtime手順](https://docs.k3s.io/advanced#nvidia-container-runtime-support)に従います。
   Toolkit導入後にK3sを再起動し、`kubectl get runtimeclass nvidia`で確認します。
   ドライバーは実際に使用する検証済みリリースのCUDA要件に合わせます。
3. 4090筐体上で読み取り専用の確認を行います。

   ```sh
   python3 scripts/gpu/rtx4090-preflight.py
   ```

   対象外OS・アーキテクチャ、4090以外、複数GPUを拒否します。これはホストの確認であり、モデル検証ではありません。
   推論部分だけでrequestsはCPU 3.25コア、RAM 14.5GiB、memory limitsの合計は28GiBです。
   モデル取得用init container、OS、K3s、アプリ、DB等は別です。
   これは設定値であり、筐体全体の実測最低スペックではありません。筐体のRAMとCPUは別途確認してください。
   モデルPVCは計40GiBを要求し、コンテナ層、動画、DBの容量も必要です。
4. 単一ノードに明示的な対象ラベルを付けます。

   ```sh
   NODE=REPLACE_WITH_LOCAL_NODE_NAME
   kubectl label node "$NODE" videoq.io/inference-target=rtx4090
   ```

5. NVIDIA Device Plugin v0.20.1を共有設定で導入します。

   ```sh
   helm upgrade --install nvdp nvidia-device-plugin \
     --repo https://nvidia.github.io/k8s-device-plugin \
     --version 0.20.1 --namespace nvidia-device-plugin --create-namespace \
     -f charts/videoq-inference/examples/rtx4090-device-plugin.yaml
   kubectl get node "$NODE" -o jsonpath='{.status.allocatable}'
   ```

   `nvidia.com/gpu.shared: 3`が公開され、専有の`nvidia.com/gpu`が公開されていないことを確認します。
   `renameByDefault: true`で共有枠を専有GPUと区別し、`failRequestsGreaterThanOne: true`で複数枠の要求を拒否します。
   複数枠の取得は計算資源やVRAMの増加を保証しません。
   このvaluesファイルはNVIDIAのchart用であり、VideoQの推論chartに渡すものではありません。

## 推論とアプリの導入

マージ前の非公開の実機受入では、レビュー対象のソースchartと、そのソースからビルド・脆弱性検査した
イメージを不変のレジストリdigestで固定します。ソースSHA、ビルド・検査結果、イメージとモデルの識別情報を保存します。
preflightはdigestの形式と割り当てを確認しますが、署名・attestationを検証するものではありません。
この試験を署名付きリリースや本番昇格として扱わないでください。
通常の署名付き配布はmain限定のため、レビュー・マージ後に実行し、本番反映前の別ゲートとします。

以下のコマンドは、今回の変更をレビュー・マージ・配布した後の、署名付きリリースによる導入経路です。

[署名付きリリースの取得・検証](on-premises-releases.md)を行います。
リリースには今回の共有GPU対応chartが含まれている必要があります。
候補のローカルchartと古いリリースを組み合わせて、候補版の署名付き受入が済んだことにしないでください。

```sh
INFERENCE_CHART=/secure/videoq-release/videoq-inference-REVIEWED_VERSION.tgz
APPLICATION_CHART=/secure/videoq-release/videoq-REVIEWED_VERSION.tgz
helm upgrade --install inference "$INFERENCE_CHART" \
  --namespace videoq --create-namespace \
  -f charts/videoq-inference/examples/rtx4090.yaml \
  -f /secure/videoq-release/verified-inference.json
kubectl -n videoq rollout status deployment/videoq-inference-embedding --timeout=30m
kubectl -n videoq rollout status deployment/videoq-inference-whisper --timeout=30m
kubectl -n videoq rollout status deployment/videoq-inference-chat --timeout=30m
python3 scripts/gpu/rtx4090-preflight.py --node "$NODE" --namespace videoq
```

最後の確認は、同じノード上のReadyな3つのPod、共有枠の割り当て、不変のイメージdigestを要求します。
各コンテナでCUDAのFP16演算と実際のengine healthを確認し、物理GPU UUIDがすべてホストの1枚と一致することを確認します。
JSONは受入証拠として非公開で保存してください。これはモデル品質や全学習経路の受入完了を意味しません。

アプリはサイト用設定に`local-ai-vllm.yaml`を重ね、署名検証済みのイメージ固定を最後に適用します。
既存の秘密情報、ストレージ、非公開URLは維持し、クラウドAIのデフォルト設定を残さないでください。

```sh
helm upgrade --install videoq "$APPLICATION_CHART" --namespace videoq \
  -f /secure/videoq-site.yaml \
  -f charts/videoq/examples/local-ai-vllm.yaml \
  -f /secure/videoq-release/verified-images.json
```

閉域運用では先にモデルを取得し、`downloadModels=false,networkPolicy.denyEgress=true`を設定します。
K3s側のNetworkPolicy enforcementも必要です。このとき推論のegressは同一リリースのpeer readinessとCoreDNSだけ許可します。
アプリ側のNetworkPolicyやホストの外部通信制限も合わせて検証してください。

## Runpodでのモデル・VRAMの予備検証

RunpodのRTX 4090 Podでは、1枚のGPU上の3つの推論プロセスで、モデルの常駐と同時推論を予備検証できます。
通常のRunpod Podはコンテナ環境で、内部のDocker/Composeには制約があります。
本番用の3つの独立した推論コンテナは維持し、K3sの割り当て・Device Plugin・NetworkPolicy・アプリ全体は、
GPU付きVMまたは実際の4090筐体で別途確認します。Runpodでの成功をK3s受入完了とは扱いません。

予備検証の起動引数は、今回のHelm設定から生成します。モデル、リビジョン、別名、VRAM予算を二重管理しません。
違いはloopbackへのbind、埋め込み用ポートを8001にすること（本番では別Podなので両方8000）、モデル保存先だけです。

1. 前述の手順で、レビュー済みruntimeの署名とdigestを検証します。
   既存の署名付きruntimeと候補ソースを組み合わせる非公開試験では、runtimeのソースと候補の
   `apps/inference/whisper`に差分がないことを別途確認し、両方のソースとイメージdigestを記録します。
   これはソースの同一性の確認であり、候補chartへの署名ではありません。
2. 変更をコミットしてcleanなcheckoutから、新しい計画ファイルをローカルで生成します。

   ```sh
   HELM_BIN=helm node scripts/gpu/export-rtx4090-probe.mjs \
     /secure/videoq-release/verified-inference.json /secure/rtx4090-probe-plan.json
   ```

   この操作でクラウドの起動、認証情報の送信、課金は発生しません。未コミット差分のある計画でGPU試験は実行できません。
3. 起動前に現在の料金と、総費用・時間の上限を確定します。GPUはRTX 4090を**1枚だけ**選びます。
   正確なイメージのCUDAに対応したホストドライバー、RAM、イメージ・約13GBの重み・キャッシュ用ディスクが必要です。
   現在確認済みのイメージはCUDA 13.0.2です。空きがない場合に別GPUや別イメージへ黙って変えません。
   provider側にも自動終了を設定し、既存サイトのvolumeや本番・利用者の認証情報は渡しません。
4. 正確なdigest固定のruntime内に、レビュー済みソースと計画を配置します。
   イメージ既定の`vllm serve`は予備検証用にentrypointを変更する必要があります。
   Runpod REST APIの`dockerEntrypoint`と`dockerStartCmd`がこの指定に対応します。推論ポートの一般公開は不要です。

   ```sh
   python3 scripts/gpu/runpod-rtx4090-probe.py provision /secure/rtx4090-probe-plan.json \
     --model-root /tmp/videoq-probe-models --output /tmp/videoq-provision-result \
     --max-seconds 1800
   python3 scripts/gpu/runpod-rtx4090-probe.py probe /secure/rtx4090-probe-plan.json \
     --model-root /tmp/videoq-probe-models --output /tmp/videoq-probe-result \
     --max-seconds 1800
   ```

   取得が完了してから、3モデルをofflineで起動します。日本語チャット、実際の1536次元の埋め込み、
   checksum固定の公開FLEURS音声の文字起こしを3回同時実行します。既存と同じtimestamp検査とCER 0.25未満を要求します。
   VRAMとGPU使用率は0.5秒ごとに記録します。観測した最大値は厳密なallocatorの最大値やVRAM保証ではありません。
5. `result.json`と用途別の非公開ログを回収してから、自分で作成した使い捨てPodとディスクを終了します。
   成否を問わずスクリプトが停止するのは、自身が起動したプロセス群だけです。
   スクリプトのdeadline・cleanupは課金制御ではないため、provider側・操作者による終了確認も必要です。
   レポート内の宣言イメージは、実際のRunpod Pod設定と外側で照合してください。

CPUや別GPUへの置き換えモードはなく、アプリ全体・K3s・本番受入の成功も宣言しません。
ローカルのHTTP・プロセスfixtureは、失敗時の拒否と終了処理のテストであり、GPUモデルの実行証拠ではありません。

参考: [Runpod GPU一覧](https://docs.runpod.io/references/gpu-types)、
[コンテナの制約](https://docs.runpod.io/tutorials/pods/build-docker-images)、[現在の料金](https://www.runpod.io/pricing)。

## 更新と実機受入

モデルやVRAM予算を変更する前に処理の投入を止め、3つの推論Deploymentをすべて0にscaleし、Podの終了後に更新します。
旧設定と新設定が混ざると、個々の設定の上限内でも合計VRAMを超える可能性があります。
PVCは保持し、rollbackでは設定とイメージ固定を組で戻します。アプリの永続データはbackupの隔離復元で確認します。

実機では次を検証して証拠を残します。

- 物理GPU 1枚、共有3枠、3コンテナすべてで同じ4090上のCUDA演算。
- 初回取得、順序付き起動、キャッシュ起動、個別再起動。PendingやOOMがなく、ホストRAM・VRAMピーク・遅延を計測できること。
- 実動画アップロード→GPU文字起こし→GPU埋め込み・索引→GPUでの引用付きストリーミング回答。埋め込みは正しいモデルの1536次元であること。
- 教材処理と学習者チャットの同時実行。CPU・クラウドへの暗黙のフォールバックがないこと。
- 実教材の日本語品質、ツール呼び出し、保護された動画の引用再生、backup/restore、更新/rollback。
- 正確な候補ソースに対する必須CIとNVIDIAイメージの脆弱性検査。レビュー・マージ後、本番昇格の前に対応するmainリリースの署名付き配布と匿名pullを確認します。

実機受入が終わるまでPRはDraftに維持します。メモリに収まらない場合も、埋め込みや文字起こしを黙ってCPUへ移さず、
モデル調整や明示的なジョブ・モデルの切り替えで3用途のGPU実行という要件を維持します。

参考: [NVIDIA Device PluginのGPU共有](https://github.com/NVIDIA/k8s-device-plugin/tree/v0.20.1#shared-access-to-gpus)、
[vLLMのメモリ設定](https://docs.vllm.ai/en/latest/configuration/engine_args/)。
