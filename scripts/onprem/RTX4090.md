# RTX 4090 1枚で VideoQ を起動する

Ubuntu の専用 GPU VM に、native K3s・DB・ストレージ・キュー・3つの CUDA 推論サービス・VideoQ をまとめて導入します。CPU 用のモデルへ切り替えず、GPT-OSS 20B、EmbeddingGemma 2、Whisper large-v3-turbo が同じ4090に常駐します。

インストーラーは通常ユーザーで動きます。ソース取得、GitHub認証、リリース検証、Helm/Kubernetes操作、設定・秘密情報の保存はそのユーザーで行います。APT、ドライバー、K3sサービス、Docker/containerd、systemdユニットの設定だけsudoを使います。K3s自体のシステムサービスはroot、API・Worker・GPU推論プロセスはコンテナ内の非root UIDで動きます。

## 必要なホスト

- Ubuntu 22.04 / 24.04、amd64、systemd のあるVMまたは実機。通常のコンテナ型Podでは使えません。
- RTX 4090 24GBを1枚、CPU 8コア以上（推奨16以上）、使用可能なRAM 32GiB以上（推奨48GiB以上）。
- ディスク200GB以上、初回導入時の空き90GiB以上。モデルとイメージに約100GBを使い、動画保存用PVCは既定40GiBです。local-pathの容量はディスク予約・使用量制限ではありません。
- sudoが使える通常ユーザー、インターネット接続。GitHub CLIのログインは必要に応じて案内されます。ローカル推論用の有料APIキーは不要です。

VM標準のNVIDIAドライバーを再利用します。[CUDA 13.0のドライバー要件](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html)に合わせ、580.65.06未満または未導入の場合はUbuntuの推奨ドライバーを導入し、必要なら一度再起動します。既存のsudo設定でパスワード不要の実行が認められている場合は、同じ通常ユーザーで自動再開します。それ以外は再起動・SSH再接続後に同じコマンドで再開してください。sudo権限やパスワードを新たに保存・永続付与しません。再起動後もGPUを認識しない場合は停止し、再起動を繰り返しません。GPUパススルーとSecure Bootの設定はVM提供者側の条件です。

## 研究室内HTTPSの設定

初回はネットワーク設定を自動生成します。通常はIP・URL・証明書方式を入力する必要はありません。

| 項目 | 既定の自動設定 |
|---|---|
| 待受IP | `0.0.0.0`（全IPv4） |
| ブラウザ用URL | 検出したLANのIPv4から `https://192.168.…` を生成 |
| 証明書方式 | 内部CAで自動発行・更新 |

```text
HTTPS接続設定: 待受 0.0.0.0:443 / URL https://192.168.10.20 / 証明書 internal
管理者ユーザー名 [site_admin]: yuki
管理者メールアドレス: ...
```

稼働中のインターフェースからLANのIPv4を検出し、Docker・K3sのブリッジや一般的なVPN用インターフェースは除外します。プライベートIPv4があれば優先します。候補が複数の場合だけIPの選択を求め、検出できない場合はURLを尋ねます。`--url`を指定すれば検出・選択を省略できます。再実行時はIPを再検出してURLを変えず、保存済み設定を使います。

待受IPは既にこのマシンへ割り当てられたIPv4を指定します。`0.0.0.0`は全IPv4での待受です。NICの設定・IP固定・DHCP予約は変更しません。固定IPまたはDHCP予約と、研究室のネットワークからTCP 443への接続許可を管理者に用意してもらってください。URLに名前を使う場合は研究室内DNS等でその名前をマシンのIPへ向けます。URLにはIPを直接使うこともできます。

| 方式 | 用途 | 利用端末の準備 |
|---|---|---|
| 内部CA (`internal`) | ドメインを持たない研究室、プライベートIP | 完了時に取り出される `tls/root-ca.crt` を各PC・ブラウザの信頼ストアへ登録 |
| 持ち込み (`provided`) | 大学・組織の発行証明書 | 発行元CAが未登録の場合は、そのルートCAを各端末へ登録 |
| 公開ACME (`acme`) | インターネットから到達可能な公開DNS名・専用IPv4 | 公的CAのため通常は追加登録不要 |

内部CA方式はCaddyが証明書を自動発行・更新します。インターネットからの着信や外部DNSでの検証は不要です。インストーラーは公開CA証明書だけを `~/.local/share/videoq-rtx4090/tls/root-ca.crt` に取り出し、それを明示的に信頼してHTTPS・動画ストレージの疎通を確認します。証明書検証を無効にした接続は行いません。各利用端末へCAを信頼登録するまではブラウザ警告が出るため、警告を無視して利用せずCAを登録してください。配布するのは `root-ca.crt` のみで、CaddyのCA秘密鍵や `tls.key` は配布しません。CAの鍵は `caddy-data` PVCに保持されるため、そのPVCもバックアップ対象です。

`--tls-mode provided`を指定すると、PEM形式の証明書（サーバー証明書・中間証明書の順）、秘密鍵、必要なら検証用ルートCAのパスを尋ねます。秘密鍵はパスワードなしのPEMを使います。証明書の期限、URLに対応するSAN、鍵の一致を確認し、導入先の `tls/` に0600で保存します。Kubernetes Secretとして非rootのCaddyだけへ読み取り専用でマウントし、鍵の内容を引数・ログへ出しません。証明書の更新は発行元側で行い、新しいPEMを指定して再実行してください。CAファイルを省略した場合、インストーラーはOSの信頼ストアを使って検証します。

API・動画ストレージは同じHTTPS originを使います。研究室内運用ではルーターのインターネット向けポート転送は不要です。待受IPの指定はアクセス元制限ではないため、研究室限定のアクセス制限はファイアウォール・VLAN等で設定してください。DB・キュー・GPU推論・Kubernetesの管理ポートを利用者向けに開放する必要はありません。

公開ACMEは外部TCP 443からマシンに届く経路が必要です。共有IPとランダムな外部ポートを使うVast.aiでは、VM内の443番を開いても外部443番は使えません。現在のVast検証環境は既存のlocalhost構成を維持し、研究室内HTTPSへ自動移行しません。

## 起動

リポジトリのチェックアウトがある場合、必要なコマンドは1つです。

```bash
bash scripts/onprem/install-rtx4090.sh
```

管理者ユーザー名とメールアドレスを対話入力し、起動後に初回パスワードを非表示で2回入力します。パスワードは引数・環境変数・設定ファイル・ログに保存しません。空欄で進めると、最後に表示される短時間・一度限りのリンクをブラウザで開いて設定できます。外部メール送信は行いません。ドライバー導入に伴う再起動後は、導入先の`install.log`で進捗と完了を確認し、`admin-setup.json`から初回設定リンクを取得できます。

ソース取得も含めた新規ホスト用の1行コマンド（sudoが使える通常ユーザー。この変更のmain反映後）:

```bash
curl -fsSL https://raw.githubusercontent.com/videoq-jp/videoq/main/scripts/onprem/install-rtx4090.sh | bash
```

開発ブランチの検証中は、取得するスクリプトとチェックアウト先を同じブランチに固定してください。

```bash
curl -fsSL https://raw.githubusercontent.com/videoq-jp/videoq/feat/rtx4090-shared-inference/scripts/onprem/install-rtx4090.sh | VIDEOQ_SOURCE_REF=feat/rtx4090-shared-inference bash
```

自動設定を変更する場合だけIP・URL・証明書方式を引数で指定できます。特定のIPだけで待ち受ける例:

```bash
bash scripts/onprem/install-rtx4090.sh \
  --listen-ip 192.168.10.20 --url https://192.168.10.20 --tls-mode internal
```

大学発行の証明書を使う例（URLの名前をDNSで解決できること）:

```bash
bash scripts/onprem/install-rtx4090.sh \
  --listen-ip 192.168.10.20 --url https://videoq.lab.example.ac.jp \
  --tls-mode provided --tls-cert /srv/certs/fullchain.pem --tls-key /srv/certs/key.pem \
  --tls-ca /srv/certs/university-root-ca.pem
```

公開ACMEを引数で指定する場合は `--url https://videoq.example.com --tls-mode acme` とします。URLだけを引数指定した新規導入でも、証明書方式は内部CAです。以前のバージョンで導入済みのACME設定は、そのまま維持します。

ブラウザからそのHTTPS URLへアクセスします。公開ポートは443番です。TLSを終端するCaddyも非root UIDで動かし、ホストの443番待受など必要なシステム操作だけsudoを使います。SSH転送は不要です。

既存のlocalhost構成から公開URLを変える場合は、公開経路を用意した上で明示的に移行します。ユーザー・暗号鍵・動画データは保持し、公開URLとストレージCORSを更新します。途中で停止した場合は同じ移行先へ再開します。

```bash
bash scripts/onprem/install-rtx4090.sh --url https://192.168.10.20 --listen-ip 192.168.10.20 --tls-mode internal --migrate-url
```

管理用のSSH自体は引き続き使えます。localhostだけの検証構成を選ぶ場合は `--url http://localhost:8080` を明示し、手元で `ssh -N -L 8080:127.0.0.1:8080 4090` を開きます。

## 再実行と保存先

同じコマンドは同じリリースとモデルを再適用します。既定の保存先は`~/.local/share/videoq-rtx4090`（0700）です。秘密情報・状態ファイル・初回設定リンクは0600で保存されます。既存の鍵、管理者、PVCを再生成せず、管理者の設定リンクも通常の再実行では再発行しません。

```bash
bash scripts/onprem/install-rtx4090.sh --directory ~/.local/share/videoq-rtx4090
```

自動化では `--username yuki --email you@example.com`、ストレージは初回に `--storage-gib 40` を指定できます。localhost検証モードでは初回の `--url http://localhost:18080` でポートを変更できます。通常の再実行では待受IP・証明書方式を保存した設定から再利用します。新しいIPへの変更はURL移行時に明示してください。URL、モデル空間、管理者情報、リリース、既存PVCサイズを変更しません。URL変更だけは上記の `--migrate-url` で明示できます。

既に用意した専用K3sへ導入する場合のみ `--adopt-existing` を追加します。既存のSecretがある場合は、対応する`credentials.json`を導入先に保持している必要があります。未知の鍵を自動で置き換えることはありません。

期限切れの初回設定リンクの再発行は明示的に行います。

```bash
bash scripts/onprem/install-rtx4090.sh --reset-admin-link
```

DB、動画データ、`credentials.json`は別ホストにもバックアップしてください。このコマンドはインストールと中断後の再開用です。別リリースへの更新やSQLの巻き戻し、環境削除は自動で行いません。

## 検証と配布物

- 既存のリリース検証を使い、mainの成功したGitHub Actions実行・ソースSHA・SLSA証明を照合します。現在の音声ランタイムと一致するリリースを選び、再開時はその版に固定します。
- API/Web/Workerと音声エンジンは署名検証済みイメージです。CUDA用EmbeddingGemmaはこのソースからホスト上でビルドし、containerdのdigestに固定します。このローカルビルドにはGitHubのリリース証明は付きません。
- 3つのReady Pod、同一GPU UUIDでのCUDA行列演算、API/Web疎通、S3 PUT/GET/Rangeとメディア保護ヘッダーを検証してから管理者を作成します。
- チャットはコンテキスト16384、同時処理1件、CPUへの重みの退避なし。画像内容の解析は無効です。動画の文字起こしと検索・Q&Aを対象にします。
- 現在の実測はUbuntu 22.04.5 / RTX 4090 1枚で約20GiBのVRAM使用です。初回ビルド・モデル取得には回線次第で数十分かかります。

設定は[NVIDIA Container Toolkitの公式導入手順](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/install-guide.html)と[K3sのNVIDIA runtime設定](https://docs.k3s.io/advanced#nvidia-container-runtime-support)に基づきます。通常のk3d方式の単一VPSインストーラーは[K3S.md](K3S.md)にあります。

現環境への導入と同一コマンドの再実行、鍵・PVC・管理者・モデルPodの保持を
[実機検証](../../docs/verification/native-rtx4090-install-2026-11-11.json)しています。
別のまっさらなVMでのドライバー導入・自動再起動経路は未実機検証です。
